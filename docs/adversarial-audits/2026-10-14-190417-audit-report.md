## 详细发现

### AA-UX-001 [P1] 导出失败被呈现为成功 —— HEAD 预检缺失

- **证据等级**：已验证
- **位置**：`lib/client.js` → `ExportSessionMenuItem.onSelect`
- **触发条件**：`/api/session.export` 返回任何非 2xx（401 会话过期、404 会话不存在、413 过大、500 内部错误）
- **错误行为**：
  ```js
  anchor.click();          // 无返回值，不反映 HTTP 结果
  anchor.remove();
  setState("started");     // ← 无条件执行，标签变成「正在导出…」
  ```
  用户看到「正在导出…」后**不会**得到任何失败提示；浏览器可能静默地不产生文件，或产生一个内容是 JSON 错误体的文件。
- **为何重要**：这是**静默的成功谎报** —— 直接命中攻击面清单里的「产品逻辑：错误的『默认成功』」。用户会以为 ZIP 已下载，从而**删除或关闭会话**，造成真实数据丢失。
- **机制证据（官方做法对照）**：官方 `SessionLogDownloadController.run` 先做 HEAD 预检，**只有** `response.ok` 才交棒给下载管理器：
  ```js
  const response = await this.fetcher(route, { method: "HEAD", signal });
  if (!response.ok) { const detail = await response.text().catch(() => ""); throw new Error(`Export failed: HTTP ${response.status}…`); }
  this.save(route, sessionLogZipFilename(sessionId));
  ```
  官方文档亦明确该路由同时提供 `GET`/`HEAD`（"contributes the exact `GET`/`HEAD /api/session.export` Fetch route"）。
- **修复方向**：改为 `fetch(url, { method: "HEAD" })` → 检查 `response.ok` → 通过后再触发 `<a download>`；失败时把标签切到 `sessionExportFailed` 并 `noteDegrade`。

### AA-BE-001 [P1] 状态更新落在已卸载组件上（顺序颠倒）

- **证据等级**：已验证
- **位置**：`lib/client.js` → `ExportSessionMenuItem.onSelect` 前两行
- **触发条件**：任意一次点击导出
- **错误行为**：
  ```js
  setMenuOpen(false);   // ← 先关菜单：官方菜单关闭会卸载其所有行组件
  setState("busy");     // ← 后更新状态：此时组件已卸载
  ```
  React 18 对已卸载组件调用 `setState` 不再抛错，但**不会**产生任何可见效果 —— 于是「正在导出…」这个反馈**永远不会出现**，`sessionExportFailed` 也不会出现。该功能的全部状态机形同虚设。
- **对照**：同一个文件里的 `CopySessionIdMenuItem` 顺序**恰好相反**（先 `setState('done')` 再 `setMenuOpen(false)`），说明这是本次实现引入的偏差，而非项目既有约定。
- **为何重要**：与 AA-UX-001 叠加后，「成功/失败」两条反馈路径**同时失效** —— 用户拿不到任何结果信号。
- **修复方向**：把 `setState` 放回 `setMenuOpen(false)` **之前**；或（更稳）不依赖组件状态，改用 `noteDegrade` + 官方 primitives 的 toast/临时态。

### AA-BE-002 [P2] 缺少并发折叠，连点可发起多次下载

- **证据等级**：高置信推断（静态阅读；未在真机上连点压测）
- **位置**：`ExportSessionMenuItem`（`disabled: state === "busy"` 仅在**同一个**组件实例内生效）
- **触发条件**：用户快速重复打开菜单并点击；或两个会话行的导出被连续触发
- **错误行为**：`anchor.click()` 每次都会发起一次新的 GET。**宿主的 ZIP 构建是有界的流式操作**（官方 concern 里写明 "bounded ZIP stream"），重复请求会重复 flush + 重复构建。
- **对照证据**：官方 controller 明确做了折叠 —— "One session admits one active download at a time; repeated gestures share that operation"（`this.active` Map + `done` promise）。
- **为何重要**：命中「滥用」攻击面（刷量）。单个大会话 ZIP 可达数十 MB（本机会话日志解压后 2.1 MB，压缩前更大），多次并发会占用宿主内存与磁盘 I/O。
- **修复方向**：模块级 `Map<sessionId, Promise>` 做在飞折叠；或退一步用模块级 `Set<string>` 记录在飞会话，配合现有的 `disabled` 视觉反馈。

### AA-DATA-001 [P2] 压缩计数未按 `compactionId` 去重

- **证据等级**：未验证假设（本机会话仅 1 个 summary 事件，无法证明重放会发生）
- **位置**：`lib/host-v19.js` → `contextLossProjection.apply` 的 `case 'compaction/summary'`
- **触发条件**：同一 `compactionId` 的 `compaction/summary` 被提交或重放两次
- **错误行为**：`compactions += 1` 与 `lostTokens += shadowedTokenCount` **无条件累加**，不校验 id 是否已见过 → 计数与 token 双双翻倍。
- **为何重要**：该读数存在的唯一理由是「压缩次数反映信息丢失程度」。计数失真会让用户对上下文健康度产生错误判断 —— 而这正是本功能的产品承诺。
- **降低风险的事实**：`compaction/summary` 由 loop 在 `finally` 中恰好提交一次；投影的 `apply` 是纯函数、由会话事件流驱动。**未观察到重放路径**。
- **修复方向**：在状态里保留最近 N 个（或单个）已计数的 `compactionId`，重复即跳过。注意 `stateSchema` 需同步放宽。

### AA-TEST-001 [P2] 新增功能的测试是假覆盖

- **证据等级**：已验证
- **位置**：`test/client.test.mjs` → 「渲染冒烟：会话菜单两项在 primitives 缺失时返回 null（不抛错）」
- **触发条件**：任何时候跑 `npm test`
- **错误行为**：该断言只做两件事 —— ① `typeof view === 'function'`；② 调用一次不抛错，返回值是元素或 `null` **皆可**。
  - 在本机替身环境下，`menuPrimitives()` 实际**拿得到** primitives（实测返回元素），所以这条测试**从未走过**它名字里宣称的"primitives 缺失"分支。
  - `onSelect` 内部逻辑（URL 拼装、HEAD 预检、失败处理、状态迁移）**零断言**。AA-UX-001 与 AA-BE-001 两个 P1 因此完全逃过回归。
- **为何重要**：命中「测试：假覆盖」。更危险的是它给了"已有测试保护"的错觉 —— 本次两个 P1 就是从这个缺口漏出去的。
- **修复方向**：注入假的 `document`/`fetch` 断言：① URL 含正确 `sessionId` 与 `includeDescendants`；② HEAD 非 2xx 时不触发下载且状态为失败；③ HEAD 2xx 时才产生 `<a>` 并调用 click。

### AA-CODE-001 [P3] `lastFailed` 是死数据

- **证据等级**：已验证
- **位置**：`lib/host-v19.js` 折叠并投影 `lastFailed`；`lib/client.js` 的 `ContextLossPill` **不读它**
- **触发条件**：始终
- **错误行为**：宿主为这个字段维护状态机（`compaction/start` 清位、`compaction/end` 置位），投影把它发给每一个客户端，客户端的 i18n 里也有对应文案位 —— 但**没有任何渲染分支使用它**。`grep` 确认客户端仅在两处引用（投影字段守卫与 i18n），无消费方。
- **为何重要**：跨端契约（`contracts.contextLossProjection` 已登记该字段）承诺了一个用户看不到的信息。它要么该被展示（"上次压缩失败"是有价值的告警），要么该从契约里移除。
- **修复方向**：二选一 —— 若展示，给 `ContextLossPill` 加失败态（失败时用 error 色 + 悬停说明）；若移除，删字段 + 改 `.project-architect.json` 的契约 + 删守卫断言。

## 已验证为**正确**的部分（避免只报坏消息）

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| URL 注入 | **安全** | `encodeURIComponent(sessionId)` 已用；`EXPORT_ROUTE` 是常量 |
| 路径穿越（`anchor.download`） | **安全** | 文件名含 sessionId，但 DSH 会话 id 为 `session-<uuid>` 字符集；且 `download` 属性由浏览器净化 |
| 鉴权 | **正确** | 走同源 Cookie（`cookieValue(rawCookie, cookieName(authority))`），`<a>` 同源导航自动携带 |
| 压缩折叠语义 | **正确** | 只有 `summary`/`prune` 计数，`start`/`end` 不算 —— 失败/取消的压缩不会被误记 |
| token 非法值 | **正确** | `shadowedTokensOf` 对非有限数、负数一律按 0，不编数 |
| 投影缺席降级 | **正确** | `ContextLossPill` 在投影为 null 时返回 null，官方布局零影响 |
| 零值语义 | **正确** | 未压缩时显示「尚未压缩过上下文」而非隐藏（0 是真实读数，不是缺数据） |
| 状态引用变更 | **正确** | 折叠对无关事件返回原引用；压缩事件必然产生新引用（投影可见性的硬要求） |
