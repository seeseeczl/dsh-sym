## 威胁与失败模型

- **资产 A1**：工作区源码与未提交改动 —— `reset --hard` / `revert` 的直接破坏面。
- **资产 A2**：会话日志目录 —— 删除不可撤销，父目录与同工作区其它会话共用。
- **资产 A3**：计费读数 —— 用户据此判断成本，**错价不报错**比报错更有害。
- **资产 A4**：用户手工维护的 `prices.json` —— 表达力不足会把"纠错"逼成"更大的错"。
- **攻击者能力**：① 借注入让用户点一下（= 一次同源 `fetch`，POST JSON 也可）；
  ② 连点确认按钮；③ 构造 `branch` / `commit` / `sessionId` 字段。
- **最贵失败**：① `--hard` 被**重复执行**，把两次点击之间刚 stash / 刚保存的东西一并清掉；
  ② 仓库已被改变、界面却说"失败"，用户重试触发 ①；
  ③ 计费把某厂商整族模型算成 0 元却只显示"未定价"，用户据此做决策。

## Findings 详情

### [P1] AA-CONC-001 — 破坏性 git 写不幂等，连点即二次执行 — `lib/host-v21.js:createGitStatusReader.reset / revert`

- **证据等级**：已验证（静态路径确定，不依赖运行时）
- **触发条件**：确认框「确定」在 `busy === "write"` 判真之前被双击/回车连发（同一帧内两次点击
  都读到旧的 `disabled={busy === "write"}`）；或任一脚本对 `/api/sym.git` 连发两次
  `{action:'reset', mode:'hard', commit}`。
- **错误行为**：`reset()` **没有任何"这个动作是否已在执行"的判断**。第一次把 HEAD 移到目标
  并丢弃未提交改动；第二次**再把同一个 `--hard` 跑一遍**。`revert()` 只在 `REVERT_HEAD` 存在时
  拒绝，而成功的 `revert` 会把那个状态提交掉 —— 于是**同一提交可被回滚两次**（生成"撤销的撤销"）。
- **影响**：① 不可逆的数据丢失（用户在第一个成功提示与第二次点击生效之间完全可能 `git stash`
  或刚保存文件）；② 历史静默污染。两次都**成功返回**，UI 只会说"已重置/已回滚"。
- **最小修复方向**：宿主侧维护"进行中的写"表（按 cwd + 动作 + 参数），同一项在执行时第二次
  直接 `409 busy`；客户端 `write()` 入口按 `busy` 短路。**宿主那道是真闸门**，客户端只是省一次往返。
- **关联优化任务**：AA-OPT-001

### [P1] AA-CONC-002 — 写成功后读数抛错，会把"成功"翻成"失败" — `lib/host-v21.js:gitStatusRoute.write` + `reader.read` 调用点

- **证据等级**：已验证
- **触发条件**：`git reset` / `git revert` / `git revert --abort` **已经成功**，紧随其后的
  `payload: await read(cwd, signal)` 抛错（signal 被导航中断、子进程被杀、输出超限、编码异常）。
- **错误行为**：三个写函数都写成 `return { ok: true, payload: await read(cwd, signal) }`。
  `read()` 一抛，`ok:true` 那行根本没执行，异常冒到路由的 `catch` → `outcome = null`
  → 返回 **500 `{ok:false, message:'git action failed.'}`**。
- **影响**：仓库已经变了，界面却说"失败"。用户重试 → **直接触发 AA-CONC-001 的二次执行**。
  这是两条 P1 的组合伤害：单看每一条都不致命，串起来是"失败提示 + 数据丢失"。
- **最小修复方向**：**写成功即成功**——把 `read()` 包一层，失败时 `payload` 给 `null`
  （客户端已能处理 `payload === null`），绝不把 `ok:true` 翻成失败。
- **关联优化任务**：AA-OPT-002

### [P1] AA-SEC-003 — 客户端把「宿主明确拒绝」当成「连不上宿主」 — `lib/client.js:CommitLogView.write` / `commitLog.load`

- **证据等级**：已验证
- **触发条件**：宿主返回 403/409/415/503（版本不匹配、被中间件拒绝、写忙碌）。
- **错误行为**：`catch` 分支把**任何**异常都归成"连不上宿主"（删除会话）或
  `describeError(failure)`（提交记录）。真正的 4xx 原因（宿主 `message`）只在 `response.ok === false`
  且 JSON 可解析时才会显示；而 `response.json()` 在响应是纯文本时返回 `null`，
  届时文案退化成裸状态码 `"409"`。
- **影响**：用户按"网络问题"去排查（重启 App、查代理），而实际是权限/冲突/版本问题。
  与 AR-10-13「桌面版没有 DevTools，错误不可见」叠加，这条会显著拉长故障定位时间。
- **最小修复方向**：区分 `fetch` 抛错（网络）与 `response.ok === false`（宿主答复）；
  后者按状态码给**本地化文案**，宿主原文只进降级日志（1.8.4 的 AUD 整改已确立这个口径）。
- **关联优化任务**：AA-OPT-002

### [P2] AA-MONEY-004 — `prices.json` 表达力不足，错价无法纠正成"未知" — `lib/host-v21.js:priceBook`

- **证据等级**：已验证
- **触发条件**：用户想 ①把某个模型从"有时段价"改成"无时段价"；②屏蔽一条错误的内置价目。
- **错误行为**：`peakPriced` 只能显式打开（`entry.peakPriced === true`），**无法显式关闭**；
  任何数值都被 `num()` 变成数字，给 `null` 也变 `0` —— 于是"纠正错价"只剩"改成 0"这一条路，
  把错价变成"免费"，比错价更误导。
- **影响**：用户有心纠错，被逼成更大的错。
- **最小修复方向**：`peakPriced` 三态（缺省=继承 / 显式 `true` / 显式 `false`）；
  增加显式"移除价目"语义（`unpriced: true` 或 `null`），界面显示"未定价"而不是 0 元。
- **关联优化任务**：AA-OPT-003

### [P2] AA-MONEY-005 — 报价簿为空时静默把非 DeepSeek 用量算成 0 元 — `catalogDirectory` / `readCatalog`

- **证据等级**：已验证（静态）
- **触发条件**：`process.resourcesPath` 与 `execPath` 推导都找不到 `app.asar/dsh/node_modules/@earendil-works/pi-ai/dist/providers/data`；
  或该目录里的 `.json` 全部没有 `cost` 字段（上游 schema 改名）。
- **错误行为**：`readCatalog` 返回空索引 → 非 DeepSeek 模型全部进 `unpriced`，金额按 0 计。
  只有一条 `noteDegrade` 进控制台 —— 而**桌面版没有 DevTools**（AR-10-13）。界面上"未定价"
  与"真 0 元"极易混淆。
- **影响**：花费读数系统性偏低且不报警，用户据此做成本判断。
- **最小修复方向**：`catalogSize === 0` 时在花费面板给一处**可见**提示；`unpriced` 非空时把
  "未计价的 token 数"单独计数并展示。
- **关联优化任务**：AA-OPT-003

### [P3] AA-LOGIC-006 — 引用索引"最后写入者胜"，前缀撞车时可能指错回复 — `proseForPrefix`

- **证据等级**：已验证（逻辑确定，但触发需 ID 前缀碰撞）
- **触发条件**：两条消息 id 的前 12 位十六进制相同（UUIDv4 下概率约 2⁻⁴⁸，实际不可能；
  但**外部注入了自定义 id 的消息**或未来改用非 UUID id 时不再成立）。
- **错误行为**：`Map` 迭代顺序 = 插入顺序，循环不 break，最后一条命中者胜 —— 即**较新**的那条。
  用户引用较早的那条，展开的却是较新回复。
- **影响**：低概率、可察觉（引用内容对不上），但会让"引用"功能失去可信度。
- **最小修复方向**：命中多于一条时视为**歧义**，返回 null（标记原样保留），而不是猜一个。
- **关联优化任务**：AA-OPT-004

### [P3] AA-OPS-007 — `priceBook()` 在每条计费事件里都 stat 一次 `prices.json`

- **证据等级**：高置信推断（调用点 `apply` 的 `assistant/message` 分支与 `viewOf` 已确认）
- **触发条件**：长会话、高频结算事件（每次工具调用后都可能有 `assistant/message`）。
- **错误行为**：`priceBook()` → `readOverrides()` → `statSync` 每次都跑；mtime 变了还得整本
  重建（`new Map(baseBook...)` 深拷贝）再重建视图。稳态下是每事件一次同步 stat。
- **影响**：事件循环上的同步 I/O；绝对量不大（一次 stat 微秒级），但在宿主主线程上属于可消除的抖动。
- **最小修复方向**：按 mtime 做短 TTL（例如 1s）缓存 stat 结果，或把 overrides 读取移到
  `viewOf` 单点（折叠只看 holidays，可在事件里用缓存副本）。
- **关联优化任务**：AA-OPT-004

## 测试与观测缺口

- **缺失用例**（170 项回归里**一条都没覆盖**）：
  1. 同一写参数连发两次 → 第二次必须被拒；
  2. `read()` 抛错时写操作仍须 `ok:true` 且 `payload === null`；
  3. 客户端对 4xx 的文案必须来自本地字典，不得退化成裸状态码；
  4. `prices.json` 三态 `peakPriced` 与"移除价目"；
  5. `proseForPrefix` 歧义时返回 null。
- **缺失观测**：宿主没有"写操作已执行"的审计事件；`noteDegrade` 只在控制台（桌面版不可见），
  "报价簿为空"这类**全局**降级用户完全感知不到。

## 残留风险

- `sessionPersistence.locate()` 的真实返回形状已从 asar 取证（`join(sessionDir(root,cwd,id), file)`，
  父目录恒为该 id 的编码段），因此原计划的"basename 守卫"**降级为纵深防御**，不算 finding；
  但服务实现若随 DSH 版本变动，这条前提需要重验。
- 多窗口并发删除同一会话未实测（当前串行化粒度是单进程内）。
- AA-OPS-007 的性能影响未做基准测量，只确认了调用路径。

## 总评

- **结论：阻塞**（3 条 P1，均有可复现的代码路径与明确修复方向；其中两条会**组合**成数据丢失）。
- **前置条件**：AA-CONC-001 / AA-CONC-002 / AA-SEC-003 修复并补回归后具备发布条件；
  P2 两条建议同批（AA-MONEY-004/005 直接对应本项目"错价不报错"的立场）。

### [P2] AA-CONC-008 — 写锁按"动作+参数"分键，两条并发 `switch` 会**都执行** — `exclusiveWrite`

- **证据等级**：已验证（`node -e` 直跑，见下）
- **触发条件**：`switch main` 与 `switch feat/x` 同时在飞（用户连点两行分支，或双击）。
- **错误行为**：第一版把键写成 `cwd + 动作 + 参数`，两条 `switch` 是**不同的键**，于是都进锁、
  都执行。实测 git 输出 `['switch -- main', 'switch -- feat/x']` —— 两条都跑了，
  谁最后落地取决于调度，而**两次都返回 `ok: true`**。
- **影响**：最终分支不确定，界面两次都说"已切换"。工作区的写本来就没有"并行"一说
  （git 自己也用 `index.lock` 串行）。
- **修复**：锁改成**一条 cwd 一个门**（`inFlightWrites: cwd → key`），第二份无论参数是否相同
  都给 `busy`。修复后实测：`A=true, B=busy`，`switch` 只执行一次。
- **守卫**：新增回归「并发切到不同分支时，第二条被拒」；原「不同 mode 不该互相阻塞」那条
  按新语义改写为「同一工作区同一时刻只允许一个写」。
