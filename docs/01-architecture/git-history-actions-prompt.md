# 提示词：在提交列表里实现「重置到此处 / 回滚到此处 / 回滚此次提交」

> 这份文件是**给实现者（人或 AI）的提示词**，不是说明文档。照它做出来的东西应该与
> dsh-sym 1.8.3 里那三个行内按钮行为一致。方括号 `[...]` 里是要替换成你自己环境的值。

---

## 一、你要做的东西

在一个**分页的 git 提交列表**里，每一行末尾放三个小图标按钮，让用户能：

| # | 按钮 | 一句话语义 |
|---|---|---|
| 1 | **重置到此处** | 分支退回到这笔提交，但**改动全留在工作区**（不丢东西） |
| 2 | **回滚到此处** | 分支退回到这笔提交，**后续提交和未提交改动全部丢弃**（破坏性） |
| 3 | **回滚此次提交** | 在分支顶部**新建一个反向提交**抵消这笔，**历史不改写** |

三个都是**本地操作，永不推送**。

---

## 二、三个动作的精确语义

### 按钮 1「重置到此处」→ `git reset --mixed`

```
git reset --mixed <完整哈希> --
```

- 分支指针退回目标提交；目标之后的提交**离开分支**（但对象还在 reflog 里）
- 这些提交的内容**以及**用户未提交的改动，**全部留在工作区**
- **不会丢任何数据**，所以用**黄色**（state-warn）

### 按钮 2「回滚到此处」→ `git reset --hard`

```
git reset --hard <完整哈希> --
```

- 分支指针退回；目标之后的提交离开分支
- **目标之后的全部提交 + 所有未提交改动被丢弃**
- 工作区被覆盖成目标提交的状态
- **不删除未跟踪文件**（`--hard` 不碰 untracked）——文案里必须写清这一点，否则会吓到人
- 无法撤销，所以用**红色**（state-error）

### 按钮 3「回滚此次提交」→ `git revert --no-edit`

```
git revert --no-edit <完整哈希> --
```

- 在分支顶部**新建一个反向提交**抵消目标提交的改动
- **原有历史不改写**
- 冲突时 git 停在一半，必须给用户一个「中止这次回滚」的出口（见第五节）
- 用**红色**（state-error）

## 三、UI 规格

**触发说明**：悬停或键盘聚焦时立刻显示说明。**不要用原生 `title`** —— 浏览器要求鼠标停顿
约 1 秒才弹，快速划过等于没有提示，用户会以为按钮坏了。

**文案**（悬停提示，一句话说清动作与代价）：

```
重置到此处（保留全部改动）
回滚到此处（丢弃后续提交与所有未提交改动，无法撤销）
回滚此次提交（生成反向提交，历史不改写）
```

⚠ 每一条都必须带**括号里的代价说明**。只说"重置到此处"而不说会丢什么，等于没提示。

**图标**：16 格 viewBox、1.3 描边、无填充的线性图标，渲染框 20px。

```
重置到此处     M3.4 8a4.6 4.6 0 1 1 1.5 3.4M3.4 5.4v3.1h3.1      （逆时针弧 + 箭头）
回滚到此处     M8 3.6 3.6 8 8 12.4M13.4 3.6 9 8l4.4 4.4          （双左箭头）
回滚此次提交   M4 8.2h6.2a3.2 3.2 0 0 1 0 6.4H7.4M4 8.2l3-3M4 8.2l3 3  （弯曲回返箭头）
```

**颜色**：直接对应"会不会丢东西"，不要统一灰色。

| 按钮 | 颜色 | 依据 |
|---|---|---|
| 重置到此处 | 黄（warn） | 不丢数据 |
| 回滚到此处 | 红（error） | 会丢数据 |
| 回滚此次提交 | 红（error） | 会丢数据（虽然可再 revert 回来） |

形状负责区分两个红色动作，颜色负责回答"危险吗"。

**尺寸**：按钮 20×20，图标 13–14px，三个之间的间距 4–8px。
⚠ 20×20 低于 WCAG 建议的 24×24，桌面端可接受但不理想；若你的场景要照顾触屏，放大到 24。

## 四、二次确认（不可省略）

点击按钮**只弹确认框，不发任何请求**。这是硬约束：

```
行内按钮 onClick → 只写一个"待确认"状态，不 network
确认框「取消」/ Esc / 点别处 → 只清状态
确认框「确认」→ 这里才唯一一次发请求
```

确认框结构是**标题 + 一句正文**，别再堆三段：

```
标题：重置到 16c1886？
正文：1.8.3：对话视图第三个标签改为提交记录
      （空行）
      分支退回这一笔，改动都留在工作区，不会丢东西。
```

- 标题只回答"对哪一笔做什么"
- 正文第一行是**该提交的标题**（让用户确认没选错行）
- 正文第二段是**后果**，一句话

破坏性那条（按钮 2）必须给出**具体数字**，不能只写"所有未提交改动"：

```
后续提交与 3 个文件的未提交改动都会被丢弃，无法撤销。
```

这个 `3` 要从 `git status` 真实数出来（**只数已跟踪文件**——`--hard` 不删未跟踪文件，
把它们算进去是误导）。工作区干净时改说"工作区是干净的，没有改动会丢"。

**确认框的样式必须与宿主应用的对话框一致**，不要自己发明。要点：

- 宽度 `min(380px, 100vw - 32px)`，内距 `22px 24px 24px`，圆角 `24px`
- 标题 `16px / 500 / line-height 24`，正文 `14px / line-height 22`
- 按钮 `min-height: 44px`、圆角 `12px`、**竖排**、间距 `8px`
- **背景必须不透明**（半透明会让背后的表格文字透上来，看起来"糊在一起"）
- 加约 50% 的全屏遮罩
- 危险动作用标题和正文表达，**确认按钮本身不必上色**——行内的红图标已经喊过一次了

**焦点管理**（`aria-modal` 只是声明，浏览器不会替你拦 Tab）：

- 打开时焦点进入弹窗（落在第一个按钮）
- Tab / Shift+Tab 只在弹窗内的按钮间循环
- 关闭后焦点**还给触发它的那个图标按钮**，不是掉回 body

## 五、宿主侧实现（写 git 的那一端）

如果你的架构是"客户端 + 宿主"两半，**所有 git 写操作都必须在宿主**——客户端不该直接跑命令。

### 统一的写操作纪律

1. **argv 数组，不要拼 shell 字符串**。每个参数独立传，末尾加 `--`
2. **提交 id 先解析成完整哈希**：`git rev-parse --verify <id>^{commit}`
   - 用户传进来的可能是任何东西（含 `--force`）；解析失败就拒绝
   - 下游全部用解析后的完整哈希寻址
3. **mode 用封闭枚举校验**：`soft | mixed | keep | hard`，枚举外**在跑 git 之前**就拒绝
4. **写操作用自己的超时 signal，不复用请求的 signal**
   - 页面导航会 abort 请求 signal；把一次 reset 从中间掐断更糟
5. **git 拒绝时如实回传 stderr 首行**，不要包装成"操作失败"

### 三个动作的调用

```
重置到此处    reset --mixed  <hash> --
回滚到此处    reset --hard   <hash> --
回滚此次提交  revert --no-edit <hash> --
```

`--no-edit` 是必须的：宿主没有终端，git 不能尝试开编辑器。

### 冲突与半途状态

`revert` 冲突时 git 会停下并留下一个**进行中**的状态。你要：

1. 进入前先检查有没有未完成的回滚，有就拒绝（否则两个状态会搅在一起）
2. 冲突时返回**挡路的文件名列表**给界面
3. 界面提供「中止这次回滚」，它执行 `git revert --abort`

⚠ **检查用的是 `REVERT_HEAD`，不是 `CHERRY_PICK_HEAD`。**
这一点很容易搞错：只查 `CHERRY_PICK_HEAD` 会让"已有回滚在进行"的保护完全失效，
之后每次 revert 都被 git 以 `you have unmerged files` 拒绝，而界面没有任何出口。
稳妥做法是**两个都查**（merge / cherry-pick / revert 都可能留下类似的半途状态）。

## 六、六个已踩过的坑（照抄结论，别重犯）

### 1. `git log` 的记录分隔是 `<NUL><换行>`，不是单纯的 `<NUL>`

用 `--format=...%x00` 时，git 会在 NUL 之后**另起一行**。按 NUL 切出来的每一段都带一个
前导 `\n`，直接校验 `%H` 会把**每一个提交**都判成坏行。

表现：**列表永远为空，且不报任何错**。

修法：切完先剥掉行首的 `\r?\n` 再校验。

### 2. 确认框要显式定位

如果你复用一个"下拉菜单"的样式类（它通常是 `position: fixed` 但没有 `left/top`），
把它拿来当对话框会出问题：`fixed` + `auto` 会被放在**元素本来该在文档流里的位置**。
对话框一般是被 portal 到 `body` 末尾的 → 它落在**页面最底部**，常在视口之外。

表现：**点了按钮什么都没发生**（其实确认框渲染了，只是你看不见）。

修法：对话框必须自己写 `left/top/transform` 居中，别继承菜单的定位。

### 3. 半透明的对话框背景会让背后内容"透上来"

菜单类常带 `backdrop-filter`（毛玻璃）。小菜单上没问题，但**需要细读的确认框**上，
背后的表格文字会糊成一层杂讯。

修法：对话框用**实色**背景，不要 `backdrop-filter`，并加遮罩。

### 4. `parseGitStatus().files` 是**数字**，不是数组

如果你要拿它算"几个文件有改动"，直接用 `files`。
写成 `files.length` 会得到 `undefined`，而这个字段会**静默地传不到界面**——
表现是"破坏性确认里没有具体数字"，看起来像功能没做。

### 5. 改样式时回头检查旧调用点

两个真实事故，都是同一类错误：

- 把一个类从"文字按钮"改成"20×20 图标按钮"后，另一个**用文字**的按钮还在用这个类
  → 六个字被压进 20px
- 在 `a + b ?? c` 里，`??` 对字符串拼接不生效 → 属性恒为 `"keep:undefined"`

**改了共享的类或工具函数，一定要全局搜一遍调用点。**

### 6. 守卫测试必须反向验证

写了断言不等于它抓得住问题。真实案例：断言"代码里要有 `event.preventDefault()`"，
把目标那行删掉后测试**照样通过**——因为文件别处也有 `preventDefault`。

**做法**：故意把关键代码改坏 → 跑测试 → 确认它**失败** → 还原。
不失败就说明断言太宽，要收紧（限定在目标函数/分支的上下文里）。

## 七、验收标准

做完了要能通过这几条：

- [ ] 点任意一个按钮，**网络面板里没有任何请求**（只有确认后才发）
- [ ] 确认框在屏幕中央、背景不透明、背后的表格读不出来
- [ ] 三个按钮的黄/红与"会不会丢数据"一致
- [ ] 破坏性那条的确认框里有一个**具体文件数**，且与 `git status` 对得上
- [ ] Tab 在确认框内循环，出不去；Esc 关闭后焦点回到触发按钮
- [ ] `reset --hard` 之后，未跟踪的新文件**仍然存在**（验证它没被误删）
- [ ] `revert` 造一个冲突 → 界面出现「中止这次回滚」→ 点它之后仓库能继续正常操作
- [ ] 悬停提示**立刻**出现（不是等一秒）

## 八、一条原则

这三个按钮里，**只有「重置到此处」可以放心点**。

其余两个会丢东西。所以颜色、"具体会丢几个文件"、二次确认这三样**必须同时存在**——
少任何一个，用户都会在不该点的时候点下去。
